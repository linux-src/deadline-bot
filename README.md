# deadline-bot

Telegram-бот для контроля временных изменений (баннеры, акции, загрузочные
экраны и т.п.), реализованный по ТЗ «Для контроля временных изменений».

Бот отвечает на один вопрос: **что сейчас временно активно и когда это нужно
убрать**. Каждое изменение обязательно содержит описание, боты, где оно
действует, срок удаления или следующей проверки и ответственного сотрудника.
Бот публикует карточку в отдельный чат/тему, сам присылает напоминания,
помечает просрочку и отслеживает её, пока изменение не подтвердят убранным.

## Стек

- Python 3.11+, [aiogram 3](https://docs.aiogram.dev/) — сам бот и FSM-мастер создания
- SQLite (`aiosqlite`) — хранение изменений и списка сотрудников
- APScheduler — ежеминутная проверка сроков, напоминания, эскалация просрочек

## Установка и запуск

### Локально

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# заполнить BOT_TOKEN, CARD_CHAT_ID и т.д.

python bot.py
```

### В Docker

```bash
cp .env.example .env
# заполнить BOT_TOKEN, CARD_CHAT_ID и т.д.

docker compose up -d --build
docker compose logs -f      # логи
docker compose restart      # применить изменения .env
docker compose down         # остановить (данные в ./data останутся)
```

База SQLite хранится в `./data` на хосте (смонтирована volume'ом) — переживает
пересборку и рестарт контейнера.

Зависимости ставятся офлайн из закоммиченной папки `wheels/` (`pip install
--no-index --find-links=./wheels`) — сборка не обращается в PyPI вообще, ни
локально, ни в CI, ни на сервере. Это осознанный выбор ради воспроизводимости
(сборка не сломается, если PyPI недоступен или лежит) и работы в
сети-ограниченных окружениях. Обратная сторона: колёса собраны под
`manylinux x86_64 / Python 3.12` — на ARM (Apple Silicon, Raspberry Pi,
ARM-инстансы в облаке) сборка не пройдёт. Если нужно обновить зависимости
или добавить архитектуру, перегенерируй папку:

```bash
python3 -m venv /tmp/wheelenv && /tmp/wheelenv/bin/pip install -q --upgrade pip
/tmp/wheelenv/bin/pip download -r requirements.txt -d wheels \
  --only-binary=:all: --platform manylinux2014_x86_64 \
  --python-version 312 --implementation cp --abi cp312
```

и закоммить обновлённую `wheels/`.

### Privacy mode бота (@BotFather → /setprivacy) — обязательно Disable

Чтобы весь мастер `/temp` (описание, ручной ввод даты и т.д.) работал прямо
в группе, а не только в личке, privacy mode должен быть **выключен**:
`@BotFather → /mybots → выбрать бота → Bot Settings → Group Privacy → Turn
off` (то же самое, что `/setprivacy → Disable`). Без этого Telegram не
доставляет боту обычные текстовые сообщения в группах (только команды и
обращения по имени), и любой шаг со свободным текстом там зависнет без
ответа.

Чтобы узнать `CARD_CHAT_ID` (и `CARD_THREAD_ID`, если карточки должны идти в
отдельную тему супергруппы) — добавьте бота в нужный чат и отправьте там
`/chatid`, бот пришлёт оба id.

**Важный нюанс:** смена privacy mode в BotFather применяется только к новым
вступлениям бота в чат — если бот уже состоял в группе до переключения,
Telegram не применит новую настройку задним числом. Если после Disable
текст всё ещё не доходит именно в этой группе — удали бота из участников и
добавь заново.

### Меню команд в Telegram

При старте бот сам регистрирует список команд через `setMyCommands`
(`/temp`, `/active`, `/today`, `/chatid`) — они появляются в системном меню
«/» у любого пользователя без ручной настройки в BotFather.

## CI/CD

`.github/workflows/docker-publish.yml` при каждом пуше в `main` собирает
Docker-образ и публикует его в GitHub Container Registry:
`ghcr.io/linux-src/deadline-bot:latest` (и дополнительно тег с коротким
SHA коммита — удобно откатиться на конкретную сборку). Сборка не требует
секретов, кроме встроенного `GITHUB_TOKEN`.

Если пакет в GHCR приватный (по умолчанию — как видимость репозитория),
на сервере перед первым `pull` нужно один раз залогиниться:

```bash
echo <PERSONAL_ACCESS_TOKEN> | docker login ghcr.io -u <github-username> --password-stdin
```

Токену достаточно прав `read:packages`. Либо сделать пакет публичным в
настройках репозитория на GitHub (Packages → deadline-bot → Package
settings → Change visibility) — тогда логин не нужен.

## Деплой на сервере

На сервере не нужен исходный код целиком — только `docker-compose.prod.yml`
и `.env`, образ приезжает готовым из GHCR:

```bash
mkdir -p /opt/deadline-bot && cd /opt/deadline-bot

curl -fsSL -o docker-compose.yml \
  https://raw.githubusercontent.com/linux-src/deadline-bot/main/docker-compose.prod.yml
curl -fsSL -o .env.example \
  https://raw.githubusercontent.com/linux-src/deadline-bot/main/.env.example
cp .env.example .env
nano .env   # заполнить BOT_TOKEN, CARD_CHAT_ID и т.д.

# если пакет приватный — см. логин выше
docker compose pull
docker compose up -d
```

Обновление на новую версию после очередного пуша в `main`:

```bash
cd /opt/deadline-bot
docker compose pull
docker compose up -d
```

(при желании — обычная строка в cron, раз в день, или отдельный вебхук от
GitHub Actions, который по SSH дёргает эти же две команды; я это не
настраивал, см. «Идеи на будущее»).

База данных лежит в `/opt/deadline-bot/data` — бэкапить нужно именно её
(`deadline_bot.db`), контейнер можно пересоздавать сколько угодно раз без
потери истории изменений.

## Переменные окружения (`.env`)

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | токен из @BotFather |
| `CARD_CHAT_ID` | чат/супергруппа, куда публикуются карточки и уведомления |
| `CARD_THREAD_ID` | (опц.) id темы внутри супергруппы |
| `BOTS` | список ботов через запятую, между которыми распределяются изменения |
| `TIMEZONE` | часовой пояс для расчёта сроков (по умолчанию `Europe/Moscow`) |
| `REMINDER_MINUTES_BEFORE` | за сколько минут до срока слать напоминание (по умолчанию 60) |
| `ESCALATION_MINUTES` | с каким интервалом повторять «ПРОСРОЧЕНО», пока не подтвердят (по умолчанию 45) |
| `DB_PATH` | путь к файлу SQLite |

Если `CARD_CHAT_ID` не задан, бот на первое время публикует карточку прямо в
тот чат, откуда была вызвана `/temp` — но это временное решение только для
обкатки, для продакшена id чата нужно указать.

## Сценарий работы (как в ТЗ)

1. **`/temp`** (или кнопка «➕ Новое временное изменение» после `/start`) —
   запускает пошаговый мастер: тип изменения → где действует (все боты /
   один / несколько с чекбоксами) → описание → срок (точная дата или «нет
   точной даты» → быстрые опции проверки) → ответственный. На каждом шаге,
   кроме первого, есть кнопка **◀️ Назад** — если промахнулся с выбором, не
   нужно начинать заново: она возвращает на предыдущий шаг с уже введёнными
   данными (например, отмеченные боты никуда не пропадают). Всплывающие
   подменю («Изменить», «Продлить», подтверждение удаления по нескольким
   ботам) точно так же можно закрыть кнопкой **◀️ Назад** / **❌ Отмена**, не
   трогая саму карточку.
2. По завершении бот публикует карточку **ВРЕМЕННОЕ ИЗМЕНЕНИЕ** с кнопками
   `✅ Убрано`, `⏰ Продлить`, `✏ Изменить` в настроенный чат.
3. Планировщик раз в минуту проверяет сроки:
   - за `REMINDER_MINUTES_BEFORE` минут шлёт `⏰ Напоминание`;
   - в момент дедлайна шлёт `🔴 Срок истёк` / `🟠 Наступило время проверки`
     и переводит статус в «Просрочено» / «Требует проверки»;
   - дальше каждые `ESCALATION_MINUTES` минут повторяет `⚠ ПРОСРОЧЕНО`, пока
     изменение не подтвердят убранным.
4. **`✅ Убрано`** — если бот был один, изменение сразу завершается. Если
   ботов несколько, бот спрашивает «Убрано во всех?» → «Да, везде» или
   «Выбрать боты» (чек-лист по каждому боту); пока не отмечены все — задача
   остаётся активной.
5. **`⏰ Продлить`** — быстрые опции (+1/+2/+3 часа, до конца дня, до
   завтра, своя дата) или свободный ввод даты; карточка обновляется, статус
   сбрасывается на «Активно», отправляется уведомление было/стало.
6. **`✏ Изменить`** — точечное редактирование описания, ботов, срока или
   ответственного без пересоздания карточки.
7. **`/active`** — список всех незавершённых изменений со статусом.
8. **`/today`** — то, что нужно убрать/проверить/продлить/подтвердить
   сегодня (плюс всё, что уже просрочено или требует проверки, независимо от
   исходной даты) — для поддержки в начале смены.

Статусы: 🟡 Активно · 🔴 Просрочено · 🟠 Требует проверки · ✅ Завершено.

## Решения, принятые за пределами буквального текста ТЗ

ТЗ описывает поведение примерами, но не фиксирует несколько технических
деталей — вот как они закрыты и почему:

- **Список сотрудников для «Ответственный».** В ТЗ не сказано, откуда он
  берётся. Бот автоматически регистрирует в списке любого, кто хоть раз
  написал ему (даже `/start`) — специальной админки для этого не нужно.
  Если создатель — единственный, кто писал боту, список будет состоять из
  него одного; попросите коллег, которые должны быть ответственными,
  написать боту `/start`.
- **Ввод даты и времени.** Кнопки «Выбрать дату и время» реализованы как
  запрос текста в формате `20:00`, `12.09 20:00` или `12.09.2026 20:00` —
  полноценный календарь Telegram inline-клавиатурами не рисуется, это
  избыточно для сценария «сегодня/завтра/через N часов».
- **Цвета статусов.** В примере `/active` из ТЗ значок первых двух пунктов
  визуально не совпадает с их же разделом «Статусы» (вероятно, артефакт
  PDF/иконок). Реализация следует явному определению из раздела «Статусы»:
  🟡 Активно, 🔴 Просрочено, 🟠 Требует проверки, ✅ Завершено.
- **«Все боты» и контроль по нескольким ботам.** Выбор «Все боты»
  разворачивается в полный список ботов из `BOTS` и дальше отслеживается
  так же, как явный выбор нескольких ботов (чек-лист при завершении) — в
  ТЗ это не оговорено явно, но пример чек-листа по ботам в разделе «Контроль
  нескольких ботов» подразумевает именно это.
- **Требует проверки → эскалация.** ТЗ описывает повтор «ПРОСРОЧЕНО» только
  для изменений с точным сроком удаления. Для изменений «без точной даты»
  реализована аналогичная периодическая эскалация (`⚠ ТРЕБУЕТ ПРОВЕРКИ`) —
  иначе такие задачи тихо повисали бы без напоминаний до следующего
  ручного /active.
- **Бот-админка отдельно от отдельного бота в чат поддержки.** ТЗ упоминает
  обе идеи. Реализован второй вариант (отдельный бот, публикующий карточки
  в конкретный чат) — он гибче: этот же бот и есть «админка» (создание,
  редактирование, списки), просто без отдельного веб-интерфейса.

## Структура проекта

```
bot.py                  # точка входа, регистрация роутеров и команд
config.py               # переменные окружения
Dockerfile              # офлайн-сборка из wheels/
docker-compose.yml       # локальная сборка (build: .)
docker-compose.prod.yml  # продакшен: готовый образ из GHCR (image: ...)
wheels/                  # закоммиченные .whl всех зависимостей
.github/workflows/
  docker-publish.yml     # CI: сборка + публикация образа при пуше в main
app/
  db.py                 # SQLite: employees, changes
  utils.py              # даты, статусы
  cards.py              # текст карточек/уведомлений, refresh_card
  keyboards.py          # инлайн-клавиатуры
  states.py             # FSM-состояния
  middlewares.py        # автоregистрация сотрудников
  scheduler.py          # APScheduler: напоминания, просрочки, эскалация
  handlers/
    registration.py     # /start, /chatid
    wizard.py            # /temp — мастер создания
    card_actions.py      # кнопки карточки: Убрано/Продлить/Изменить
    lists.py             # /active, /today
```

## Итоги

Бот полностью реализует сценарий из ТЗ (создание, карточка, напоминания,
просрочки, продление, контроль по нескольким ботам, `/active`, `/today`),
упакован в Docker, автособирается и публикуется в GHCR при пуше в `main`,
разворачивается на сервере двумя файлами без исходного кода. Меню команд
в Telegram настроено автоматически.

## Идеи на будущее (не реализовано, но стоит рассмотреть)

- **Персистентное хранилище FSM.** Сейчас прогресс мастера `/temp` живёт в
  памяти процесса (`MemoryStorage`) — рестарт контейнера на середине шага
  сбрасывает мастер. Для мелкой команды не критично, но `RedisStorage`
  или свой SQLite-backed storage сделают это устойчивым к деплоям.
- **Автообновление на сервере.** Сейчас `docker compose pull && up -d`
  нужно запускать руками (или самому повесить на cron/systemd-timer).
  Можно добавить Watchtower или webhook-эндпоинт, который CI дёргает по
  SSH сразу после публикации образа — тогда сервер обновляется без
  ручных действий.
- **Автотесты в CI.** Сейчас корректность проверяется вручную (smoke-скрипты
  при разработке), в пайплайне нет тестового шага перед сборкой образа.
  Стоит завести `tests/` с pytest и гейтить публикацию образа зелёным прогоном.
- **Права/роли.** Ответственным можно назначить любого, кто хоть раз написал
  боту — для маленькой команды ок, но нет способа кого-то исключить из списка
  или ограничить, кто вообще может создавать изменения (`/temp`).
- **Бэкапы БД.** SQLite-файл ничем не защищён от потери диска на сервере —
  стоит добавить хотя бы ежедневный cron с копией `data/deadline_bot.db`
  куда-то за пределы сервера (S3, другой хост).
- **Уведомление о падении бота.** Если процесс/контейнер упадёт, никто не
  узнает, кроме как заметив, что напоминания перестали приходить. Простой
  heartbeat во внешний аптайм-монитор (UptimeRobot, healthchecks.io) закрыл
  бы это дёшево.
- **Команда `/cancel`.** Если пользователь застрял на шаге мастера и просто
  хочет выйти, сейчас единственный путь — начать `/temp` заново (это чистит
  старое состояние). Отдельная явная команда была бы понятнее.
- **Мультиарх Docker-образ.** `wheels/` сейчас только под x86_64 — если
  понадобится ARM-сервер, потребуется либо второй набор колёс, либо
  вернуть сборку на обычный `pip install` с доступом в сеть.
